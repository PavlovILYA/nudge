# Nudge 0.5.0, build 7 — PR #6

Settings показывает **0.5.0.7** из фактических CFBundleShortVersionString/CFBundleVersion. Apple marketing version остаётся трёхчастной 0.5.0. Build приложения и Widget Extension — 7. IPA: `Nudge-0.5.0-7-Unsigned.ipa`; device artifact: `Nudge-0.5.0-7-iOS-Device-Unsigned`. Git SHA в bundle не добавлен: для этой задачи достаточно build и привязанного к артефакту CI commit.

## Что установлено кодом и тестами

### Продолжение диктовки

Уязвимый переход: begin создаёт новую сессию → TextField при снятии фокуса повторно записывает прежний текст → прежний setter безусловно вызывал edit и обнулял voiceSession → update новой сессии больше не принимался. Это воспроизведено детерминированным тестом буфера; оно не доказывает порядок UIKit callbacks конкретного физического воспроизведения.

Теперь одинаковый commit — no-op, запись из TextField во время захвата не принимается, фокус снимается при старте. Устаревшие onChange text/busy проверяются против текущего состояния. Настоящая ручная правка по-прежнему инвалидирует старую сессию; следующий begin создаёт новую. DictationTranscriber, PCM, накопление по интервалам и единственный редактор сохранены. Проверяется цикл dictate → edit → dictate → edit → dictate, включая повторный commit и старые результаты.

### Минуты после системного Stop

Прежний код создавал следующий сигнал под тем же ID, который останавливает AlarmKit. [Apple описывает автоматическую обработку Stop системой](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit), но не гарантирует приложению порядок этой обработки относительно custom intent. Это зависимость от системного порядка, а не подтверждённая по device trace причина конкретного случая пользователя.

После выполнения экземпляра теперь отменяется старый ID, сохраняется новый ID регистрации и регистрируется следующий сигнал с прежним UUID задачи и новым токеном экземпляра. Записи сериализуются по UUID задачи, включая смену alarmID. Intents несут отдельно UUID задачи, occurrenceID и alarmID; запоздавшие команды старой регистрации не затрагивают новую. Intents прежних сборок без параметра alarmID сопоставляются только с исходным ID задачи, поэтому после смены регистрации тоже безопасны. Тест моделирует удаление старого системного ID уже после возврата intent: новый сигнал сохраняется. Покрыты интервалы 1/2/5 минут, повторный Stop, один сигнал и завершение всей серии. Уже выданное разрешение AlarmKit используется без повторного запроса из фонового intent.

**Сценарий A:** Stop должен сохранять выполнение и ставить следующий сигнал. При ошибке сохраняются история, pending date, новый токен и видимая ошибка; открытие Nudge позволяет восстановить будущее планирование. Успешность реального вызова/срабатывания на заблокированном iPhone требует проверки.

**Сценарий B:** без взаимодействия с первым сигналом новый каждую минуту не регистрируется. Одна задача имеет одно ожидающее выполнение и один сигнал. Нет таймера, polling, бесконечной очереди или обещания произвольного фонового запуска. Это также объясняется в UI выбора повторений.

### Actions и закрытие без выбора

[AlarmManager.stop(id:)](https://developer.apple.com/documentation/alarmkit/alarmmanager/stop(id:)) синхронно останавливает сигнал и удаляет одноразовую fixed-регистрацию. Actions не вызывает CompleteTaskIntent.

Порядок: сохранить pending date +5 минут → вызвать stop старого ID → сохранить новый ID → зарегистрировать запасной сигнал → открыть Actions. Его время и то, что закрытие сохраняет сигнал, видны в окне. Явный Snooze заменяет запасной сигнал, Turn off отменяет его. Повторный старый Actions только открывает окно, не сбрасывает срок; старый Stop не завершает задачу после перехода к новой регистрации. Исходный срок, occurrenceID, правило и Calendar от Actions/Snooze не меняются.

Запасной сигнал ставится заранее, поэтому после успешной регистрации закрытие окна, swipe dismiss, отмена навигации или завершение процесса не требуют callback. Если процесс прерван **внутри** последовательности до регистрации, в SwiftData остаётся pending operation; ближайшее открытие приложения повторяет её. Без завершения этой операции нельзя гарантировать сигнал через 5 минут при принудительном убийстве процесса. При ошибке stop/schedule состояние остаётся активным с ошибкой; будущая регистрация не выдаётся за успешную. Восстановление теперь охватывает и одноразовые задачи с pending Actions.

Foreground intent требует штатной разблокировки. Нельзя обещать прекращение вибрации до Face ID/до фактического запуска intent. `stop` не переназначает аппаратные кнопки и не обходит системную защиту.

### Snooze и версия

Ползунок 1–120 и редактируемое целое поле 1–1440. Больший ввод не обрезается: ползунок остаётся у края, показано пояснение. Пустые/нулевые/отрицательные/дробные/слишком большие значения запрещены. Перенос — только явной кнопкой, в том числе над цифровой клавиатурой. Быстрые 5/10/15/30/60 работают одним нажатием; DatePicker сохранён.

Версия читается из Bundle.main.infoDictionary. CI проверяет соответствие CFBundleVersion настройкам проекта и совпадение версий приложения/виджета; имя IPA/артефакта выводится из собранного Info.plist. Старое жёсткое значение build 6 удалено из workflow.

## Автоматические проверки и данные

Добавлены/сохранены тесты буфера, числового ввода/шкалы, версии, минут 1/2/5, позднего системного удаления старого ID, Actions/запасного сигнала/повторного intent/35 минут/выключения, восстановления после schedule error. Тесты не вызывают системных разрешений, реального звука или вибрации.

SwiftData-схема не менялась. UUID, Calendar identity, история, исходный срок, звуки и правила старых задач не сбрасываются. alarmID меняется только при явном переходе к новой регистрации после Stop/Actions, не при миграции. Сохраняются миграционные fixtures прежних версий. Данные/приложение удалять не требуется.

Локальные CLI проверки чистых структур не равны iOS-сборке или проверке миграции. CI выполняет Release Simulator/Device, unit-тесты и проверяет вложенный Widget Extension/ресурсы. По указанию пользователя CI запускается без ожидания и polling. Успех финального прогона заранее не заявляется.

## Обязательная проверка на iPhone 13 / iOS 27.2.1

1. Установить поверх прежнего Nudge тем же Apple ID/эффективным Bundle ID, без удаления. В Settings увидеть 0.5.0.7. Сверить старые задачи, звуки, повторы, Completed и Calendar.
2. Длинная диктовка → Stop → дописать `(это я написал вручную)` → Continue Dictation → Stop → правка → Continue. Полная фраза и правки сохранены без дублей. Повторить с паузами, клавиатурой, сменой фокуса и обоими Widgets.
3. Каждые 1/2/5 минут: дождаться сигнала, нажать системный Stop, увидеть Active/историю/следующий срок; дождаться ровно одного следующего сигнала. Повторить при закрытом приложении/блокировке и после повторного открытия.
4. Отдельно не взаимодействовать с первым сигналом: не ожидать автономной цепочки. Галочка завершает всю серию и отменяет следующий сигнал; после перезапуска он не возвращается.
5. На звонящем сигнале Actions: зафиксировать Face ID и момент прекращения вибрации. Задача Active, следующий сигнал примерно через 5 минут. Закрыть Actions без выбора и полностью закрыть Nudge — дождаться запасного сигнала.
6. Actions → 35 минут ползунком/числом → подтверждение с открытой клавиатурой. Один сигнал, исходный срок/правило/Calendar не меняются. Проверить 90, 120, 121, 1440 и невалидный ввод. Быстрые кнопки остаются мгновенными.
7. Actions → Turn off: нет вибрации/будущего сигнала, задача Active. Повторные Actions/Stop старой регистрации не выполняют/не воскрешают задачу. Проверить быстрые повторные нажатия.
8. При отказе AlarmKit/ошибке следующей регистрации увидеть ошибку, сохранённое выполнение/pending, выполнить retry. Отдельно проверить Calendar без дублей, русский/английский, Dynamic Type и VoiceOver.

Ни остановка физической вибрации, ни повторное физическое срабатывание этой сборки пока не подтверждены. При сбое собрать Nudge*.ips и безопасные OSLog стадии без содержимого речи. LLM — отдельный PR #7, в эти изменения не входит.
