# Flexible snooze — design, plan and Apple API research

## Design

Keep the existing ReminderStore and closure-based AlarmService boundary. Use a native sheet for a specific reminder with five one-tap intervals, a highlighted selection/preview, and a DatePicker with a single save action. Completion remains explicit. Keep scheduledAt as the original task deadline; add optional nextAlarmAt and pendingSnoozeAt. Optional additions permit inferred SwiftData lightweight migration; verify by opening a store written with the frozen 0.1.0 schema.

The alternative of a snippet returned by the alarm action has no documented guarantee of an AlarmKit presentation host. Do not ship it. A countdown only supports a preconfigured duration, not this arbitrary date picker.

Persist pendingSnoozeAt before cancelling the old alarm. Check permission before cancellation. Cancel the stable alarm ID (tolerate verified absence), then register a fixed schedule with that same ID. Finally persist nextAlarmAt and clear pendingSnoozeAt. On launch compare pending date to the actual system fixed schedule: finalize a matching registration, otherwise show an interrupted/failed operation with a manual retry. Never silently recreate a stopped alarm. Cancellation of the sheet performs no scheduling or database mutation.

2. Add interval, date, reschedule, failure, reentrancy, interrupted-operation and legacy-store migration tests using fake system closures. Exercise failing feature tests in CI before the implementation.
3. Add optional model fields, durable rescheduling and foreground reconciliation; use MainActor and the existing busy guard.
4. Add the App Intent with a String UUID parameter and foreground execution, plus a tiny observable pending-task route consumed by ContentView. No store operations in the intent.
5. Add sheet, list entry point, localized strings and version 0.2.0 (3). Check Release simulator/device builds, full simulator tests and built plist metadata in CI.
6. Review the complete diff and publish the PR for physical-device acceptance; never merge.

## Research sources

- [AlarmKit](https://developer.apple.com/documentation/alarmkit)
- [Scheduling an alarm](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)
- [WWDC25: Wake up to the AlarmKit API](https://developer.apple.com/videos/play/wwdc2025/230/): custom secondary action with LiveActivityIntent and alarm ID parameter.
- [Alert](https://developer.apple.com/documentation/alarmkit/alarmpresentation/alert-swift.struct): native stop control and optional custom secondary control. The installed SDK marks the old stopButton initializer deprecated in 26.1 and explicitly says its property is no longer used. Use the new initializer on 26.1+, retaining the old initializer only on 26.0.
- [LiveActivityIntent](https://developer.apple.com/documentation/appintents/liveactivityintent): the intent runs in the app process. This allows a MainActor observable request to bridge cold/warm app startup without an extension, URL scheme or event bus.
- [App Intent modes](https://developer.apple.com/documentation/appintents/getting-started-with-the-app-intents-framework): supportedModes = .foreground replaces openAppWhenRun (deprecated in the installed SDK at iOS 26). The latter was examined but is unnecessary at the app's minimum iOS version.
- [Authentication policy](https://developer.apple.com/documentation/appintents/intentauthenticationpolicy/requireslocaldeviceauthentication): require device unlock before accessing the task selection UI. Actual Face ID/passcode transition must be checked on iPhone.
- [Interactive snippets](https://developer.apple.com/documentation/appintents/displaying-static-and-interactive-snippets), [WWDC design guidance](https://developer.apple.com/videos/play/wwdc2025/281/): documented system hosts include Siri, Spotlight and Shortcuts. Returning a snippet does not establish a supported AlarmKit → locked-screen interactive snippet flow. Therefore use the documented foreground custom action. No Widget Extension.

The OS owns the system alert layout, stop label and, on newer systems, the custom action's visible wording (Apple describes an Open action). Supply localized Choose Time text where honored, but do not claim control over the exact rendered system label. Arbitrary SwiftUI cannot be inserted into the AlarmKit alert.

SDK evidence is generated by the existing Xcode 27 CI runner as the Apple-SDK-Reference artifact. Build/test evidence and physical acceptance are tracked in the PR and README, separately.
